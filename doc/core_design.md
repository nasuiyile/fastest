## 核心设计

兼容memcached文本协议，后续还兼容Meta协议。 每个网络线程均采取协作式调度，保留自己的Data HashMap。
线程（分片）数取进程 CPU 亲和性里的 CPU 数（`util::core_num()`，受 taskset / cgroup cpuset 限制），不是整机 CPU 数。
如果收到请求的数据，在解析后能被当前线程直接处理，那么直接完成处理，如果不能处理则投递给其他的线程。
采取协作式调度保证了，每个请求处理线程在进行网络IO操作导致空闲的时候，也能处理其他线程来的请求。

整体的线程运行机制类似于Dragonflydb的shared-nothing架构。整体采用C++20中 boost::
asio来进行协作式调度。内存调度器使用了mimalloc，因此内存分配是16字节对齐的。
网络采用io_uring+proactor模型。

每个线程持有一个收件队列：别人发来的请求，和自己发出去、带着响应回来的，都以「往返信封」为单位走这一个队列，见下文「跨分片投递：往返信封」。
收件队列配一个门铃（一个eventfd加一个标志），由同一个收件协程处理，见下文「门铃抑制与合并」。
收件队列是侵入式 Vyukov MPSC（`MpscQueue`，`src/server/comm/mailbox.h`），不使用SPSC是因为，如果要给每一个线程之间建立一个专用的通道，
会导致NxN的通道数量，并且核心数多的情况下，轮询通道也会成为性能开销。
在memcached协议中，需要顺序来回复用户的请求，因此当收到响应消息，就把该响应写到环形数组中（环形数组只是用来保证顺序回复的），每个TCP的session维护一个环形数组。

发送端先push，再按需敲接收分片的门铃：对方醒着时只读一下标志，不写fd；只有对方准备睡或已经睡着时才write eventfd。
对于TCP连接,每次启动都启动一条session协程,因此使用co_await可以停在当前连接上。
收件协程醒来后清空收件队列；只要这一轮处理了消息，就让出CPU并保持醒着，某一轮收件队列为空才在门铃fd上等待
（io_uring 后端直接 async_read 门铃，读本身就清零计数；epoll 后端 async_wait → 清 fd）。

跨分片的请求装进信封，信封记录发起分片（origin），每条记录 u64 的连接编号和 u32 的请求序号（每个连接自增，允许回绕）。

收到请求信封：被唤醒后，按到达顺序 pop 收件队列直到为空（不设上限）。请求信封逐条执行（只是纯hashmap O(1) 的操作），
由于收到的请求一定是属于当前分片的，可以直接写入对应的Data hashmap；响应原地写回同一个信封，然后把信封推回发起分片。
门铃统一敲：每攒 64 条消息先敲一次，处理回程信封前也先敲一次，一轮结束时每个发起分片最多再敲一次。

收到回程信封：把每条响应放进对应连接的环形数组，信封放回本线程的池里；写在这一轮结束时统一发起。
环形数组中数组记录了下一个需要回复给用户消息的ID。另外每个回复的ID对数组长度求余得到写入的位置。
如果 `当前回信的ID-最老的未释放ID(head)>=数组的长度`（已发送但写还没完成的槽位也占位置），那么说明环形数组满了，触发一次扩容操作。默认长度为128，扩容后更新数组长度.按每个槽保存的完整序号迁移到
seq % new_capacity。
如果收到5号槽信息，但是1号槽数据还没来，那么就继续消费队列。
如果当前回信的ID等于下一个需要给用户回复消息的ID，那么就回复消息，然后检查下一个数组的位置是否为空，如果不为空就将下一个消息也发送给用户，然后将当前回信ID自增1 。
直到下一个ID为空，那么就继续消费。写完成之后才清空已经发送的元素（写在途期间槽位被 GatherSink 引用）.

## 多分片操作

然而memcached中的命令，如get，gas是允许跨分片操作的。意味着有可能分发给多个分片多个操作的情况。因此现在环形数组收到的请求被分为了俩种，一个是多key操作的命令，一个是单key操作的命令。get等操作在第一次解析的时候就会被确定是单key还是多key。
因此将消息投递给其他线程的时候，以及回复的时候也会区分多key还是单key。如果是多key操作，会统计需要收集多少个分片的数据才能返回给客户端。因此收到回复时，会先放入到环形数组中，如果是多分片操作，那么需要等待所有分片操作全部完成，才能标记为当前数据齐全（检查就绪数组中元素的数量）。

每个value都需要维护一个u32的引用计数（侵入式计数）。用来跨线程传递，防止删除。

试过「小 value 跨分片读取时完整拷贝、计数改为非原子，大 value 仍用原子引用计数」（目标分片拷进往返信封，发起分片再物化一份），
实测不采用：9950X 上服务端单 CCD 8 核、跨 CCD 16 核，均匀访问（100 万 key）和 16 个热点 key 下，纯 GET 的拷贝版本几乎
所有点都不快于原子计数（256B～4KB 慢 2%～12%，16KB 慢 30%～50%，只有零星一两个点快 2%～6%）；SET:GET = 1:10 时按 4KB 阈值
整体比改前慢 2%～6%。原因是没有争用时两次原子操作只有几十到一百多个周期，而拷贝多了两遍 value 的读写、一次 malloc/free 和
拷贝区缓存行的跨核来回；value 发出前要在环形数组里等待有序发送，所以拷贝无法省去，序列化路径本来就是零拷贝。
要重新评估（例如多路 NUMA 机器），用 `bench/remote/ab.sh` 对比，原始数据在 `bench/results/{share,fast,ccd}-*`。

## 补充

`MpscQueue` 是侵入式 Vyukov MPSC：节点自带链接指针（继承 `MpscHook`），push 是一次 exchange 加一次 release store，
不分配内存、没有 freelist、没有 CAS 重试；只有队列所属的分片线程 pop。
同一个生产者 push 的节点按顺序取出，分片间请求的顺序保证依赖这一点。

解析时，先将当前buffer中已经到达的多条命令先解析，让这些命令自然的形成批次。

## 跨分片投递：往返信封

`Envelope`（`src/server/comm/envelope.h`）装一批发往同一个目标分片的命令，最多 16 条（`Envelope::kCapacity`）：

1. 发起分片在一个解析批次里，把发往某个分片的请求依次装进这个分片的信封（`Outbox::post`），信封从本线程的池里取；
   装满就先发出去，其余的在批次结束（`BatchScope` 析构）时发出：推进目标分片的收件队列，一次 exchange。
2. 目标分片逐条执行，把响应原地写回同一个条目（`std::variant<RequestData, ResponseData>`），标记为回程，把同一个信封推回发起分片。
   某条执行抛异常时写入 `SERVER_ERROR`，保证每个序号都有回复，连接的有序响应不会卡住。
3. 发起分片把响应放进各连接的环形数组，清空信封放回池里（每个分片最多留 64 个，多的释放）。

发件侧单独放在 `Outbox`（`src/server/comm/outbox.h`，每个 Worker 一个，线程私有）：信封装填、信封池和门铃抑制（`PendingDoorbells`）。
连接表和有序写路径放在 `SessionTable`（`src/server/comm/session.h`，同样每个 Worker 一个）：响应入环（`deliver`）、批次结束统一写（`flush_writes`）、
写完成回调、背压恢复、关闭和回收。Worker 只负责执行请求、多 key 拆分和收件循环，`BatchScope` 离开时依次调用 `Outbox::flush()` 和 `SessionTable::flush_writes()`。

信封的内存始终由发起分片分配和释放，没有跨线程 free；同步开销（队列 exchange、门铃检查）按信封付，而不是按消息付。
以前每条跨分片命令要两次堆分配（请求、响应各一次）、两次跨线程释放，boost `mpsc_weak_queue` 还要从所有线程共用的 freelist
取、还节点（每条消息约 3 次落在共享缓存行上的 CAS）。

按解析批次发送（而不是攒到事件循环一轮结束）是为了不增加延迟：流水线为 1 时信封里通常只有 1 条，省下的是分配、跨线程释放和 freelist；
有流水线时一个信封装多条，同步开销再按条数摊薄。
同一个连接发往同一个分片的命令在信封内、信封之间都保持顺序（同一个生产者 push 的信封按顺序取出），和以前逐条投递的顺序保证相同。
容量取 16：大多数信封只有几条，小容量让在途信封占的内存少（每个 1728 字节）；大批次只是多发几个信封，每条的开销几乎不变。
实测容量 16 和 64 的吞吐差别在噪声内。


流水线 1、16 连接时客户端是瓶颈，测不出差别；信封越满收益越大。批延迟的 p50/p99 没有变差。

## 门铃抑制与合并

目标是让 eventfd 写入只发生在接收方从空闲转忙的时候：对方醒着就不敲，同一批里发往同一分片的消息只敲一次。

### 门铃

每个分片一个 `Doorbell`（`src/server/comm/mailbox.h`），配合分片的收件队列：一个 eventfd 加一个 `atomic<bool> rung_`。
`Doorbell` 按 128 字节对齐，标志独占一对缓存行，不和队列的 head/tail 伪共享；fd 只读，放在同一行。
`rung_ == true` 表示门铃已抬起，生产者不必写 eventfd，因为必居其一：有人敲过门、eventfd 里有计数，消费者会醒；
或者消费者醒着，睡之前一定会放下门铃并再查一遍队列。`rung_ == false` 只出现在消费者准备睡或已经睡着的时候。

生产者（`Doorbell::ring()`，或批量时一次 `fence()` 后逐个 `knock()`）：

~~~C++
// 已经 push 完
std::atomic_thread_fence(std::memory_order_seq_cst);
if (rung_.load(std::memory_order_relaxed)) return;            // 快路径只读：对方醒着，缓存行保持共享态
if (rung_.exchange(true, std::memory_order_relaxed)) return;   // 同时看到 false 的生产者里只有一个敲门
write(event_fd_, 1);
~~~

### 收件协程

每个分片只有一个收件协程 `Worker::mailbox_loop()`，一轮（`drain_inbox()`）的顺序是：

1. 按到达顺序 pop 收件队列直到为空。请求信封：逐条执行 hashmap 操作，响应写回同一个信封，立刻推回发起分片（门铃稍后统一敲）；
2. 回程信封：先把已推回信封的门铃敲出去，不让发起分片等本线程处理响应；再把响应放进各连接的环形数组（只入环、记下连接），信封放回池里；
3. 一轮结束（`BatchScope` 析构）：敲剩下的门铃，每个记下的连接发起一次写，从不等 socket；
4. 这一轮处理过消息：`co_await asio::defer(...)` 让出 CPU 给 socket，门铃保持抬起，稍后再来一轮。
   `defer` 进本线程的私有队列，不会触发 reactor 的 interrupt；
5. 某一轮收件队列是空的：`lower()`（`rung_ = false` 加 seq_cst fence），再完整地查一遍；仍为空才在 fd 上睡，
   查到消息就 `raise()` 继续醒着。被敲醒后如果门铃是放下的（fd 里是放下之后、复查之前留下的计数），先 `raise()` 再处理。

与最初的设想（消费者醒来先复位标志、再 pop）相比，门铃在消费者醒着的整段时间里都保持抬起，并且跨轮次保持，
有流量时几乎不写 eventfd。「先清 fd、再复位标志」的顺序仍然成立：清 fd 发生在醒来时，放下门铃发生在之后准备睡时，
放下之后的敲门都留在 fd 里，不会被吞掉；最坏多一次空转的唤醒。

### 不丢唤醒

生产者「push → fence → 读 `rung_`」，消费者「`rung_ = false` → fence → 读队列」，是 Dekker 式的配对。两个 seq_cst fence 总有先后：
生产者的在前，消费者放下门铃后的复查一定能看到这条消息；消费者的在前，生产者读到的要么是 false（自己去敲门），
要么是这次放下之后别人写的 true：敲门者写的，它会敲门；消费者 `raise()` 写的，消费者醒着，睡前还会再放下、再复查一次。

Vyukov 队列的 push 分两步（交换尾指针 → 链接前驱），另一个生产者卡在两步之间时 pop 会提前返回空，排在后面的信封暂时取不到。
卡住的生产者链接完成后同样执行上面的检查，所以也不会丢。

### 批次作用域：合并投递、敲门和写

`Worker::BatchScope` 是一个作用域：作用域内发往别的分片的请求装进每个目标分片一个的信封（装满就先发出去），
发出的信封记下目标分片（`PendingDoorbells`，按分片编号去重，线程私有，不用 atomic）；
响应放进环形数组（`SessionTable::deliver`）后也只记下连接（`TCPSession::kick_pending` 去重），不发起写。
离开作用域时先 `Outbox::flush()`：把还开着的信封发出去，一次 fence、每个目标分片敲一次门铃，让对端尽早开始处理；再 `SessionTable::flush_writes()` 给每个记下的连接 `kick_write` 一次，
一次写带上这一批里该连接所有就绪的响应。一个解析批次（最多 128 条命令）和收件协程的一轮各是一个作用域。
作用域内已发出的消息每攒 64 条就先把攒下的门铃敲出去，不中断消费，只限制对端在睡时听到门铃前的延迟。
所有跨分片发送和响应入环都必须在作用域内：作用域外装进信封的请求要等下一个作用域结束才发出，入环的响应要等下一个作用域结束才写；
嵌套时内层退出也会发出信封、敲门、发起写，只是提前，不影响正确性。
作用域内不能 `co_await`：挂起前必须把信封发出去、门铃敲出去、写发起，否则对端收不到请求，响应也一直不发。
记下的连接在作用域结束前不能回收（`SessionTable::reclaim_if_idle` 检查 `kick_pending`），作用域之间待写列表总是空的。
写在途的连接不用记，写完成回调会把期间就绪的响应作为下一批发出。

以前每条响应入环就 `kick_write`，一批里第一条就绪的响应会单独发起一次写，其余的要等这次写完成再发。
现在流水线 16 时同一批的响应通常仍分两次写：本地命中的在解析批次结束时写出，跨分片的在之后的收件轮次到达。
再合并只能扣住本地响应等远端，会给它们加一个跨分片往返的延迟，所以不做。

统计计数（收件协程处理的消息数、睡下次数放在 `WorkerStats`，敲门次数、发出的信封数放在 `OutboxStats`，发起的写次数放在 `SessionStats`）只在定义了 `FASTEST_TESTING` 的测试构建中存在
（CMake 给 `fastest_protocol_tests` 打开）；生产构建里它是空类型，用 `[[no_unique_address]]` 不占空间，计数调用也不产生指令。


## 正常路径的开销

跨分片命令不得引用连接的可变输入缓冲区。解析器只复制一次 value，随后通过命令、信封和缓存移动其所有权。
批处理遍历命令引用，本地响应直接进入有序响应路径，不经过信封，也不创建错误处理协程。
多 key 的本地部分只执行一次。命令行通过 `memchr` 定位 LF；批次在首条完整命令后估算容量，减少容器扩容，空输入和未完成命令不预分配。
这些措施针对解析和路由开销；发送路径见下文「响应发送」。
