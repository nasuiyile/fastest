## 核心设计

兼容memcached文本协议，后续还兼容Meta协议。 每个网络线程均采取协作式调度，保留自己的Data HashMap。
如果收到请求的数据，在解析后能被当前线程直接处理，那么直接完成处理，如果不能处理则投递给其他的线程。
采取协作式调度保证了，每个请求处理线程在进行网络IO操作导致空闲的时候，也能处理其他线程来的请求。

整体的线程运行机制类似于Dragonflydb的shared-nothing架构。整体采用C++20中 boost::
asio来进行协作式调度。内存调度器使用了mimalloc，因此内存分配是16字节对齐的。
网络采用io_uring+proactor模型。

与Dragonflydb不同的地方在于每个线程都持有俩个mailbox，一个是用于接收别人发给自己的请求，另一个是用来接收别人发给自己的响应。因此请求响应都通过mailbox完成。
两个mailbox共用一个门铃（一个eventfd加一个标志），由同一个收件协程处理，见下文「门铃抑制与合并」。
这个mailbox是MPSC的，通过最新的库`<boost/lockfree/mpsc_weak_queue.hpp>`
来实现，不使用SPSC是因为，如果要给每一个线程之间建立一个专用的通道，会导致NxN的通道数量，并且核心数多的情况下，轮询通道也会成为性能开销。
在memcached协议中，需要顺序来回复用户的请求，因此当收到响应消息，就把该响应写到环形数组中（环形数组只是用来保证顺序回复的），每个TCP的session维护一个环形数组。

发送端先push，再按需敲接收分片的门铃：对方醒着时只读一下标志，不写fd；只有对方准备睡或已经睡着时才write eventfd。
对于TCP连接,每次启动都启动一条session协程,因此使用co_await可以停在当前连接上。
收件协程醒来后清空两个mailbox；只要这一轮处理了消息，就让出CPU并保持醒着，某一轮两个mailbox都为空才在门铃fd上等待
（io_uring 后端直接 async_read 门铃，读本身就清零计数；epoll 后端 async_wait → 清 fd）。

每次在给其他线程发送请求的时候，记录一个 origin_shard u16作为线程号，以便获取回复。i32作为tcp的id。
不同TCP的session是单独的，每个线程都维护一个u64来作为请求编号ID。
收到请求：

被唤醒后，pop请求mailbox直到为空（不设上限），然后给这些元素进行对应的操作（这理论上非常快，只是纯hashmap O (1)
的操作）。由于收到的请求一定是属于当前分片的，可以直接写入对应的Data hashmap
然后push到调用者的回复队列中。这一轮结束时每个调用者分片只敲一次门铃（每攒 64 条也先敲一次）。

收到回复：
直接通过tcp的32位fd写入回复。
环形数组中数组记录了下一个需要回复给用户消息的ID。另外每个回复的ID对数组长度求余得到写入的位置。
如果 `当前回信的ID-最老的未释放ID(head)>=数组的长度`（已发送但写还没完成的槽位也占位置），那么说明环形数组满了，触发一次扩容操作。默认长度为128，扩容后更新数组长度.按每个槽保存的完整序号迁移到
seq % new_capacity。
如果收到5号槽信息，但是1号槽数据还没来，那么就继续消费队列。
如果当前回信的ID等于下一个需要给用户回复消息的ID，那么就回复消息，然后检查下一个数组的位置是否为空，如果不为空就将下一个消息也发送给用户，然后将当前回信ID自增1 。
直到下一个ID为空，那么就继续消费。写完成之后才清空已经发送的元素（写在途期间槽位被 GatherSink 引用）.

## 多分片操作

然而memcached中的命令，如get，gas是允许跨分片操作的。意味着有可能分发给多个分片多个操作的情况。因此现在环形数组收到的请求被分为了俩种，一个是多key操作的命令，一个是单key操作的命令。get等操作在第一次解析的时候就会被确定是单key还是多key。
因此将消息投递给其他线程的时候，以及回复的时候也会区分多key还是单key。如果是多key操作，会统计需要收集多少个分片的数据才能返回给客户端。因此收到回复时，会先放入到环形数组中，如果是多分片操作，那么需要等待所有分片操作全部完成，才能标记为当前数据齐全（检查就绪数组中元素的数量）。

每个value都需要维护一个u32的引用计数（侵入式计数）。用来跨线程传递，防止删除。后期可以优化为小value直接存储+完整拷贝，大value使用引用计数。

## 补充

`<boost/lockfree/mpsc_weak_queue.hpp>` 是Vyukov MPSC，允许多个线程写入数据，只有一个线程可以读取。
读写都是无锁的。即便这个队列被设置为无界的，在没有发生扩容时，依然是无锁的（有界版本性能稍有优势）。

解析时，先将当前buffer中已经到达的多条命令先解析，让这些命令自然的形成批次。

## 门铃抑制与合并

目标是让 eventfd 写入只发生在接收方从空闲转忙的时候：对方醒着就不敲，同一批里发往同一分片的消息只敲一次。

### 门铃

每个分片一个 `Doorbell`（`src/server/comm/mailbox.h`），请求、响应两个 mailbox 共用：一个 eventfd 加一个 `atomic<bool> rung_`。
`Doorbell` 按 128 字节对齐，标志独占一对缓存行，不和队列的 head/tail 伪共享；fd 只读，放在同一行。
`rung_ == true` 表示门铃已抬起，生产者不必写 eventfd，因为必居其一：有人敲过门、eventfd 里有计数，消费者会醒；
或者消费者醒着，睡之前一定会放下门铃并再查一遍队列。`rung_ == false` 只出现在消费者准备睡或已经睡着的时候。

生产者（`Doorbell::ring()`，或批量时一次 `fence()` 后逐个 `knock()`）：

~~~C++
// 已经 push 完
std::atomic_thread_fence(std::memory_order_seq_cst);
if (rung_.load(std::memory_order_relaxed)) return;            // 快路径只读：对方醒着，缓存行保持共享态
if (rung_.exchange(true, std::memory_order_relaxed)) return;   // 同时看到 false 的生产者里只有一个敲门
write(event_fd_, 1);
~~~

### 收件协程

每个分片只有一个收件协程 `Worker::mailbox_loop()`，一轮（`drain_inbox()`）的顺序是：

1. pop 请求 mailbox 直到为空，逐条执行 hashmap 操作并把响应 push 给发送方，然后给这些发送方各敲一次门铃；
2. pop 响应 mailbox 直到为空，放进各连接的环形数组（只入环、记下连接，一轮结束时每个连接发起一次写，从不等 socket）；
3. 第 2 步处理过响应，就回头再清一遍请求 mailbox，让别的分片发来的请求最多等一次响应处理，不排到本线程所有 socket 后面；
4. 这一轮处理过消息：`co_await asio::defer(...)` 让出 CPU 给 socket，门铃保持抬起，稍后再来一轮。
   `defer` 进本线程的私有队列，不会触发 reactor 的 interrupt；
5. 某一轮两个 mailbox 都是空的：`lower()`（`rung_ = false` 加 seq_cst fence），再完整地查一遍；仍为空才在 fd 上睡，
   查到消息就 `raise()` 继续醒着。被敲醒后如果门铃是放下的（fd 里是放下之后、复查之前留下的计数），先 `raise()` 再处理。

与最初的设想（消费者醒来先复位标志、再 pop）相比，门铃在消费者醒着的整段时间里都保持抬起，并且跨轮次保持，
有流量时几乎不写 eventfd。「先清 fd、再复位标志」的顺序仍然成立：清 fd 发生在醒来时，放下门铃发生在之后准备睡时，
放下之后的敲门都留在 fd 里，不会被吞掉；最坏多一次空转的唤醒。

### 不丢唤醒

生产者「push → fence → 读 `rung_`」，消费者「`rung_ = false` → fence → 读队列」，是 Dekker 式的配对。两个 seq_cst fence 总有先后：
生产者的在前，消费者放下门铃后的复查一定能看到这条消息；消费者的在前，生产者读到的要么是 false（自己去敲门），
要么是这次放下之后别人写的 true：敲门者写的，它会敲门；消费者 `raise()` 写的，消费者醒着，睡前还会再放下、再复查一次。

Vyukov 队列的 push 分两步（交换尾指针 → 链接前驱），另一个生产者卡在两步之间时 pop 会提前返回 false，排在后面的消息暂时取不到。
卡住的生产者链接完成后同样执行上面的检查，所以也不会丢。

### 批次作用域：合并敲门和写

`Worker::BatchScope` 是一个作用域：作用域内发出的请求和响应只入队并记下目标分片（每个 Worker 一个按分片编号去重的列表，
线程私有，不用 atomic）；响应放进环形数组后也只记下连接（`TCPSession::kick_pending` 去重），不发起写。
离开作用域时先一次 fence、每个目标分片敲一次门铃，让对端尽早开始处理；再给每个记下的连接 `kick_write` 一次，
一次写带上这一批里该连接所有就绪的响应。一个解析批次（最多 128 条命令）和收件协程的一轮各是一个作用域。
作用域内每攒 64 条消息就先把攒下的门铃敲出去，不中断消费，只限制对端在睡时听到门铃前的延迟。
所有跨分片发送和响应入环都必须在作用域内：作用域外发出的消息没人敲门，入环的响应要等下一个作用域结束才写；
嵌套时内层退出也会敲门、发起写，只是提前，不影响正确性。
作用域内不能 `co_await`：挂起前必须把门铃敲出去、把写发起，否则对端可能一直睡着，响应也一直不发。
记下的连接在作用域结束前不能回收（`reclaim_session_if_idle` 检查 `kick_pending`），作用域之间待写列表总是空的。
写在途的连接不用记，写完成回调会把期间就绪的响应作为下一批发出。

以前每条响应入环就 `kick_write`，一批里第一条就绪的响应会单独发起一次写，其余的要等这次写完成再发。
现在流水线 16 时同一批的响应通常仍分两次写：本地命中的在解析批次结束时写出，跨分片的在之后的收件轮次到达。
再合并只能扣住本地响应等远端，会给它们加一个跨分片往返的延迟，所以不做。

统计计数（敲门次数、收件协程处理的消息数、睡下次数、发起的写次数）放在 `WorkerStats` 里，只在定义了 `FASTEST_TESTING` 的测试构建中存在
（CMake 给 `fastest_protocol_tests` 打开）；生产构建里它是空类型，用 `[[no_unique_address]]` 不占空间，计数调用也不产生指令。

### 实测

同机 2 核容器（GCC 13、Boost 1.92、io_uring 后端），单线程 epoll 客户端 16 连接、10000 个 key、32 字节 value，每个配置 5 轮取中位数。
eventfd 的 write()、read() 系统调用次数由 LD_PRELOAD 计数，按每个 get 请求平均（多 key get 算一次）。
改后 read() 为 0 是因为 io_uring 后端把读门铃并进了 io_uring 的提交，每次睡下仍有一次读操作，只是不再单独陷入内核：

| 配置 | 改前 ops/s | 改后 ops/s | eventfd write()/次 改前 → 改后 | eventfd read()/次 改前 → 改后 |
|---|---|---|---|---|
| 单 key get，流水线 1 | 48,341 | 50,081 | 1.00 → 0.20 | 0.36 → 0 |
| 单 key get，流水线 16 | 387,274 | 466,426 | 1.00 → 0.013 | 0.032 → 0 |
| 单 key get，流水线 128 | 1,204,846 | 1,500,604 | 1.00 → 0.0015 | 0.006 → 0 |
| 8 key get，流水线 16 | 212,025 | 237,923 | 1.99 → 0.014 | 0.044 → 0 |

同机噪声约 ±5–10%，流水线 1 的吞吐差别在噪声内。流水线 1 时客户端是瓶颈，服务端线程经常空闲，每次从空闲转忙仍要敲一次门；
要再降只能在睡前自旋一小段时间，用 CPU 换唤醒次数，暂未做。流量停止后线程正常睡眠，空闲时 CPU 为 0。

写合并（批次结束统一 `kick_write`）的实测，环境同上，16 连接，改前改后交替各跑 6 轮、每轮 4 秒，取中位数。
「每次写的响应数」是服务端发起 `async_write` 时累计的已编码响应数除以写次数：

| 配置 | 改前 ops/s | 改后 ops/s | 每次写的响应数 改前 → 改后 |
|---|---|---|---|
| 单 key get，流水线 1 | 60,762 | 60,041 | 1.0 → 1.0 |
| 单 key get，流水线 16 | 526,094 | 599,696 | 6.9 → 10.5 |
| 单 key get，流水线 128 | 1,410,433 | 1,562,432 | 57 → 81 |
| 8 key get，流水线 16 | 238,250 | 251,838 | 7.9 → 14.6 |
| set，流水线 16 | 480,837 | 549,748 | 6.9 → 10.5 |

流水线 1 不变（每批只有一条响应）；有流水线时 +6%～+14%，8 key get 的区间与改前有重叠。epoll 后端按 sendmsg 计，
流水线 16 时 sendmsg/操作 从 0.155 降到 0.097。

## 正常路径的开销

跨分片命令不得引用连接的可变输入缓冲区。解析器只复制一次 value，随后通过命令、mailbox 和缓存移动其所有权。
批处理遍历命令引用，本地响应直接进入有序响应路径，不额外创建 mailbox 消息或错误处理协程。
多 key 的本地部分只执行一次。命令行通过 `memchr` 定位 LF；批次在首条完整命令后估算容量，减少容器扩容，空输入和未完成命令不预分配。
这些措施针对解析和路由开销；发送路径见下文「响应发送」。
